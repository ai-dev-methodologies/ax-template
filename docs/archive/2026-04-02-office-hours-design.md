## Problem Statement
중소형 SI 회사는 AI를 조금씩 쓰고 있지만, 회사 차원의 통제 가능한 개발 시스템은 없다. 개발자들이 각자 AI를 활용해도 보안, 기능 정확성, 예측 가능성이 담보되지 않아 결국 기존 템플릿과 과도한 수동 검증으로 되돌아간다. 그 결과 AI는 생산성 도구가 아니라 추가 비용처럼 보이고, AX 전환이 빨라질수록 회사의 마진과 경쟁력이 흔들릴 위험이 커진다.

## Demand Evidence
현재는 강한 문제 가설 단계다. 실제 접근 가능한 SI 회사 CEO가 있고, 다음과 같은 현실 인식이 확인되었다.
- AI는 비용이 추가되는데 여전히 사람이 많이 관여해야 해서 생산성 향상이 약하게 느껴진다.
- 개발자들은 AI를 알음알음 쓰지만 회사가 공식적으로 신뢰하는 표준 생산 방식은 아니다.
- 기능 검증은 테스트 계획서와 직접 검증으로 두껍게 유지되고 있다.
- 기존 템플릿과 기존 구현 코드를 다시 참고해 품질을 방어한다.

아직 돈을 낼 정도의 명시적 구매 의사 표현은 확인되지 않았다. 따라서 초기 설계는 판매 가능한 제품을 가정하되, 첫 고객 인터뷰에서 지불 의사와 도입 장애를 반드시 검증해야 한다.

## Status Quo
현재 버티는 방식은 다음과 같다.
- AI는 조금씩 사용한다.
- 기존 SI 방식대로 테스트 계획서를 만들고 기능 검증은 사람이 직접 한다.
- 코드 품질은 처음에 만든 템플릿성 코드나 과거 구현을 다시 참고해 방어한다.

즉, AI가 코드를 빠르게 만드는 것처럼 보여도 실제 납품 프로세스는 여전히 사람 중심이다. 생산성은 부분적으로만 오르고, 신뢰 확보 비용은 계속 사람이 부담한다.

## Target User & Narrowest Wedge
### Target buyer
- 직함: CEO
- 회사 규모: 개발자, 디자이너, 관리자 포함 약 20명 조직
- 핵심 공포: AI가 비용으로만 보이고, 사람이 계속 많이 개입해야 해서 마진 개선이 안 되는 상태
- 구매 이유: 실제 업무에 바로 반영 가능하고, 개발 생산성을 올리며, 회사 고유 규율과 템플릿을 자산화할 수 있기 때문

### Narrowest wedge
첫 번째 유료 쐐기는 **React + Spring Boot 인증/보안 블루프린트 상품**이다.

이 제품은 다음을 묶는다.
1. 표준 템플릿
2. 샘플 구현
3. AI용 규칙 팩
4. 검증 기준
5. 브라운필드 적용 가이드

V1 범위는 명확히 제한한다.
- 인증: JWT 기반 access/refresh token
- 권한: role-based access control(RBAC)
- 검증: request/response validation, auth boundary, protected route 규칙
- 보안: token handling, secret/config rule, audit logging baseline
- 테스트: 인증/권한/보호 API의 최소 검증 시나리오

핵심 약속은 이것이다.
> 개발자가 AI로 인증/권한 관련 기능을 추가해도, 회사가 정한 보안/검증 기준 안에서 일관되게 구현되도록 만든다.

## Constraints
- 첫 구매자는 개발자보다 CEO 관점에서 이해되는 가치가 있어야 한다.
- 범위는 React + Spring Boot 조합에 집중한다.
- 첫 상품은 전체 플랫폼이 아니라 블루프린트 상품이어야 한다.
- AI 자체를 파는 것이 아니라, AI를 통제하는 표준화 레이어로 팔아야 한다.
- HQ의 기존 BP 문서와 consumer contract, chub freshness discipline을 재활용해야 한다.

## Premises
1. 이 제품의 본질은 AI 도입 툴이 아니라 **회사 규율이 반영된 통제 가능한 AI 개발 생산 시스템**이다.
2. 첫 구매자는 개발팀장이 아니라 **마진과 납기, 조직 생산성을 동시에 보는 CEO**다.
3. 첫 유료 가치 증명은 전체 플랫폼이 아니라 **React + Spring Boot 인증/보안/검증 표준 패키지**여야 한다.

## Cross-Model Perspective
외부 검토 결과의 핵심은 다음과 같다.
- 가장 강한 framing은 “AI 코딩 도구”가 아니라 **거버넌스와 표준화 레이어**다.
- 가장 위험한 오해는 Copilot, Cursor 같은 도구와 직접 경쟁하는 것이다.
- 첫 유료 deliverable은 `Enterprise-Safe Auth Blueprint`가 가장 적절하다.
- 기존 TypeScript 중심 pack 구조는 React 프론트와 Spring Boot 백엔드를 분리한 하위 pack 구조로 바뀌어야 한다.
- 특히 OpenAPI/Swagger 같은 계약 계층이 프론트-백엔드 경계의 source of truth 역할을 해야 한다.

## Approaches Considered
### Approach A: 인증/보안 블루프린트 상품
- 요약: React + Spring Boot 인증/권한/검증/테스트가 들어간 표준 템플릿 + 샘플 구현 + AI 규칙 팩
- 장점:
  - 데모가 쉽다
  - CEO가 가치 이해를 바로 한다
  - 이후 맞춤 pack과 운영 시스템으로 확장 가능하다
- 단점:
  - 단순 템플릿 판매로 오해받을 수 있다
  - 실제 고객 규칙 반영 정도가 약하면 차별성이 낮아질 수 있다

### Approach B: 진단 + 맞춤 BP pack 서비스
- 요약: 고객사의 기존 규칙과 납품 방식을 진단해 그 회사 전용 pack으로 정리
- 장점:
  - 돈 받기 쉽다
  - 고객 자산화 가치가 분명하다
- 단점:
  - 서비스 비중이 커진다
  - 제품화가 늦어질 수 있다

### Approach C: 팀 AI 개발 운영 시스템
- 요약: 규칙, 템플릿, 검증, 테스트 계획, AI 사용 방식을 한 번에 바꾸는 운영 시스템
- 장점:
  - 장기적으로 가장 큰 비전이다
  - 진입장벽이 높다
- 단점:
  - 첫 판매가 무겁다
  - 구현 범위가 지나치게 커질 수 있다

## Recommended Approach
**Approach A: 인증/보안 블루프린트 상품**으로 시작한다.

이유는 명확하다.
- 가장 작은 범위로도 가치가 선명하다.
- CEO가 이해하기 쉽다.
- 이미 가진 자산과 가장 잘 연결된다.
- 이후 B와 C로 확장하기 좋다.

단, 메시지는 “템플릿 판매”가 아니라 다음처럼 잡아야 한다.
> 회사 규율을 AI 위에 덮어서, 인증/보안 기능을 일관되고 검증 가능하게 만드는 블루프린트 상품

이걸 템플릿 이상으로 만드는 핵심은 **active governance**다.
- AI가 따라야 하는 규칙 팩을 같이 제공한다
- 코드 리뷰/검증 단계에서 위반 기준을 명시적으로 체크한다
- PR 단계에서 인증/보안 규칙 위반을 걸러내는 검증 스크립트 또는 체크리스트 게이트를 함께 제공한다
- 고객사는 기존 템플릿이 아니라, 반복 가능한 회사 표준을 받는다

즉 판매 단위는 "코드 뼈대"가 아니라 **샘플 구현 + 규칙 팩 + PR 검증 게이트 + 적용 가이드**다.

## Open Questions
1. 실제 CEO는 템플릿 + 샘플 구현에 돈을 낼까, 아니면 맞춤 진단형 서비스를 더 선호할까?
2. 실제 현장에서 React + Spring Boot auth/RBAC 변경 작업을 AI가 얼마나 안정적으로 따를 수 있을까?
3. SI 회사의 진짜 병목은 초기 세팅일까, 아니면 이후 유지보수와 기능 확장일까?
4. CEO가 가장 먼저 반응하는 KPI는 생산성일까, 마진일까, 납기 리스크 감소일까?
5. 고객사는 그린필드 프로젝트가 많은가, 아니면 기존 프로젝트에 붙이는 브라운필드 수요가 더 큰가?

## Success Criteria
이 설계가 맞다고 보려면 최소 아래를 만족해야 한다.
1. 첫 고객 인터뷰 3건 이상에서 문제 정의가 실제로 통한다.
2. 인증/보안 블루프린트의 가치가 템플릿 이상의 것으로 받아들여진다.
3. React + Spring Boot 기준의 pack 구조가 기존 TS-only 문서보다 분명한 이유를 가진다.
4. 샘플 구현 + 규칙 팩 + 검증 기준의 조합이 실제 납품 흐름과 연결된다.
5. 최소 Spring Boot proof-of-concept가 존재해서, 세일즈 메시지가 빈 문서가 아니라 실제 자산에 기반한다.

## Distribution Plan
초기 distribution은 다음 조합을 가정한다.
- 제품 형태: Git 기반 템플릿 저장소 + pack 문서 + AI 규칙 팩
- 전달 방식: 직접 데모 + 고객사 파일 전달 또는 private repo onboarding
- 업데이트 방식: 버전 번호가 붙은 blueprint release와 규칙 팩 release를 함께 제공한다
- 장기적으로는 zip 또는 versioned pack artifact가 필요하다
- 고객사가 air-gapped 또는 보안 심사를 요구할 가능성이 있으므로 설치/버전 고정 가능한 산출물 형태가 필요하다

MVP에서는 `chub`와 HQ consumer를 직접 고객 워크플로우에 강제하지 않는다.
- 내부적으로는 freshness 점검과 pack 관리 기준으로 활용한다
- 외부 고객에게는 우선 결과물의 안정성과 업데이트 체계로 보이게 한다

## Dependencies
- Spring Boot / Java용 pack family 정의
- React pack과 Spring Boot pack 사이 계약 계층 정의
- 인증/권한/검증/감사로그/테스트의 최소 표준 범위 고정
- 실제 SI CEO 인터뷰 및 구매 의사 검증
- 브라운필드 적용 경로 정의
- 최소 Spring Boot proof-of-concept 자산 확보

## The Assignment
다음 액션은 두 갈래다.

**1. 접근 가능한 SI 회사 CEO와 30분 인터뷰를 잡아라.**
그리고 아래 네 문장을 직접 검증하라.
1. 지금 AI가 실제로 비용으로 느껴지는가
2. 인증/보안은 반복되고 위험한 구간인가

**2. 세일즈 전에 최소 Spring Boot proof-of-concept를 만들어라.**
빈 약속이 아니라, 실제로 보여줄 수 있는 인증/권한/검증 블루프린트 자산이 필요하다.

## What I noticed about how you think
- 당신은 처음부터 "기업에 영업", "퍼스널 브랜딩", "커리어 발전"을 같이 말했다. 단순 툴이 아니라 사업 자산으로 보고 있다.
- "AI가 폭주한다"는 표현을 썼다. 속도보다 통제와 예측 가능성을 더 중요하게 본다.
- "실제 업무에 바로 반영"을 강조했다. 멋진 방법론보다 현장 투입 가능성을 먼저 보는 편이다.
- 처음엔 전체 템플릿 구조를 모두 구현하고 싶어 했지만, 대화가 진행되면서 인증/보안 블루프린트로 쐐기를 좁히는 데 동의했다. 이건 범위를 줄이는 감각이 있다는 뜻이다.
